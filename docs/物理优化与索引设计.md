# 物理优化与索引设计

本文档详细说明族谱管理系统的物理层设计决策，包括存储引擎选择、索引策略、约束设计、代际缓存机制以及查询优化过程。

---

## 一、存储引擎与字符集

```sql
ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
```

**InnoDB** 的选择理由：
- 支持事务（ACID），保证数据一致性
- 支持外键约束（FOREIGN KEY ... ON DELETE CASCADE），在数据库层维护引用完整性
- 支持行级锁，并发写入性能优于 MyISAM 的表级锁
- 聚簇索引（Clustered Index）：主键查询极快，数据行物理存储在主键 B+Tree 的叶子节点上

**utf8mb4** 的选择理由：
- MySQL 的 `utf8` 实际是 3 字节的阉割版，不支持 4 字节字符（如 emoji）
- `utf8mb4` 是完整的 UTF-8 实现，支持中文姓名（3 字节/字）和所有 Unicode 字符
- `utf8mb4_unicode_ci` 排序规则基于 Unicode 标准，中文排序更准确

## 二、索引设计

### 2.1 索引总览

| 表 | 索引名 | 类型 | 列 | 创建方式 | 用途 |
|----|--------|------|----|---------|------|
| member | PRIMARY | 聚簇索引 | member_id | `PRIMARY KEY` | 主键查询 |
| member | idx_member_name | B-tree | name | `models.Index` | 姓名精确/前缀搜索 |
| member | idx_member_name_prefix | 前缀索引 | name(10) | `RunSQL` | 减少索引体积 |
| parent_child | PRIMARY | 聚簇索引 | (parent_id, child_id) | `CompositePrimaryKey` | 复合主键查询 |
| parent_child | idx_parent | B-tree | parent_id | `models.Index` | 给定父亲找子女 |
| parent_child | idx_child | B-tree | child_id | `models.Index` | 给定子女找父亲 |
| parent_child | idx_parent_child | 组合索引 | (parent_id, child_id) | `models.Index` | 覆盖索引 |
| marriage | PRIMARY | 聚簇索引 | marriage_id | `PRIMARY KEY` | 主键查询 |
| member_generation_cache | PRIMARY | 聚簇索引 | member_id | `PRIMARY KEY` | 主键查询 |
| member_generation_cache | idx_mgc_genealogy_generation | 组合索引 | (genealogy_id, generation) | `models.Index` | 按族谱+代际查询 |

### 2.2 parent_child 表的索引设计（核心）

parent_child 表是整个系统查询最频繁的表，其索引设计直接影响递归查询和关系查询的性能。

#### 为什么需要三个索引？

parent_child 表上的查询有两个方向：

**方向 1：给定父亲 → 找子女**（后代查询、BFS 向下扩展）

```sql
-- 递归 CTE 的递归部分（后代查询）
SELECT pc.child_id FROM parent_child pc
JOIN descendants d ON pc.parent_id = d.member_id
-- 使用 idx_parent(parent_id) 或 idx_parent_child(parent_id, child_id)
```

**方向 2：给定子女 → 找父亲**（祖先查询、BFS 向上扩展）

```sql
-- 递归 CTE 的递归部分（祖先查询）
SELECT pc.parent_id FROM parent_child pc
JOIN ancestors a ON pc.child_id = a.member_id
-- 使用 idx_child(child_id)
```

B+Tree 索引是**单方向**的——`(parent_id)` 索引能高效查找 `parent_id = X`，但无法加速 `child_id = X` 的查找。因此必须为两个方向分别建立索引。

#### 复合主键的物理意义

```python
pk = models.CompositePrimaryKey("parent_id", "child_id")
```

Django 5.x 的 `CompositePrimaryKey` 在 MySQL 中映射为：

```sql
PRIMARY KEY (parent_id, child_id)
```

在 InnoDB 中，主键就是聚簇索引——数据行物理存储在主键 B+Tree 的叶子节点上。这意味着：

1. **按主键查询极快**：`WHERE parent_id = X AND child_id = Y` 直接定位到唯一行
2. **主键前缀查询也快**：`WHERE parent_id = X` 利用主键 B+Tree 的前缀匹配
3. **无额外存储开销**：主键索引就是数据本身，不需要像二级索引那样存储主键值

#### 组合索引 idx_parent_child 的作用

```sql
CREATE INDEX idx_parent_child ON parent_child(parent_id, child_id);
```

虽然主键已经是 `(parent_id, child_id)`，但组合索引仍有价值：

- **覆盖索引**：当查询只需要 `parent_id` 和 `child_id` 两列时（如 `SELECT child_id FROM parent_child WHERE parent_id = X`），可以直接从组合索引返回数据，无需回表查聚簇索引
- **更小的索引体积**：二级索引的叶子节点只存储索引列 + 主键值，比聚簇索引（存储整行数据）更紧凑，缓存命中率更高

### 2.3 member 表的索引设计

#### 姓名索引：B-tree + 前缀索引

```python
# B-tree 索引（完整列）
name = models.CharField(max_length=100, db_index=True)
# 等价于：CREATE INDEX idx_member_name ON member(name);

# 前缀索引（只索引前 10 个字符）— 通过 RunSQL 创建
migrations.RunSQL(
    sql="CREATE INDEX idx_member_name_prefix ON member(name(10));",
    reverse_sql="DROP INDEX idx_member_name_prefix ON member;",
)
```

**为什么同时需要两个索引？**

| 索引 | 查询类型 | 示例 |
|------|---------|------|
| idx_member_name（完整） | 精确匹配、前缀搜索、排序 | `WHERE name = '张三'`、`WHERE name LIKE '张%'`、`ORDER BY name` |
| idx_member_name_prefix（前缀） | 前缀搜索（更小） | `WHERE name LIKE '张%'` |

前缀索引的优势：
- **索引体积更小**：中文姓名 2-4 个字（6-12 字节），前缀索引只存前 10 字节，比完整索引小 3-10 倍
- **缓存命中率更高**：更小的索引能更多地放入 InnoDB Buffer Pool，减少磁盘 I/O

前缀索引的限制：
- **不能用于排序**：`ORDER BY name` 无法使用前缀索引
- **不能用于精确匹配后的回表优化**：前缀索引不包含完整列值

实际使用中，Django ORM 的 `name__startswith="张"` 生成的 `WHERE name LIKE '张%'` 可以使用任一索引。MySQL 优化器会根据统计信息选择更优的索引。

#### 前缀长度的选择

```sql
-- 测试不同前缀长度的区分度
SELECT
    COUNT(DISTINCT LEFT(name, 5)) / COUNT(*) AS sel_5,
    COUNT(DISTINCT LEFT(name, 8)) / COUNT(*) AS sel_8,
    COUNT(DISTINCT LEFT(name, 10)) / COUNT(*) AS sel_10,
    COUNT(DISTINCT name) / COUNT(*) AS sel_full
FROM member;
```

中文姓名的特点：
- 1 个字 = 3 字节（UTF-8），2 个字 = 6 字节，3 个字 = 9 字节，4 个字 = 12 字节
- 姓氏 1 字 + 名 1-2 字 = 2-3 字 = 6-9 字节
- 前缀 10 字符（约 3 个中文字）已能覆盖绝大多数姓名的区分度

选择 `name(10)` 是在索引体积和区分度之间的平衡点。

### 2.4 代际缓存表的索引设计

```sql
CREATE INDEX idx_mgc_genealogy_generation
ON member_generation_cache(genealogy_id, generation);
```

该组合索引服务于两类查询：

**按族谱查询所有成员的代际**（缓存重建时的比对）：
```sql
SELECT COUNT(*) FROM member_generation_cache WHERE genealogy_id = %s;
-- 使用索引前缀 genealogy_id
```

**按族谱 + 代际分组统计**（Q3、Q5 查询的核心操作）：
```sql
SELECT generation, AVG(...) FROM member_generation_cache mgc
JOIN member m ON ...
WHERE mgc.genealogy_id = %s
GROUP BY mgc.generation;
-- 使用完整组合索引 (genealogy_id, generation)
```

## 三、约束设计

### 3.1 CHECK 约束

| 表 | 约束名 | SQL | 业务含义 |
|----|--------|-----|---------|
| member | chk_member_gender | `CHECK (gender IN ('M', 'F'))` | 性别只能是男/女 |
| parent_child | chk_relation_type | `CHECK (relation_type IN ('father', 'mother'))` | 亲子关系只能是父亲/母亲 |
| parent_child | chk_parent_not_self | `CHECK (parent_id <> child_id)` | 不能自己是自己的父亲/母亲 |
| marriage | chk_spouse_not_same | `CHECK (spouse1_id <> spouse2_id)` | 不能自己和自己结婚 |

这些约束在数据库层保证数据的业务合法性，即使应用层代码有 bug，也不会产生违反业务规则的数据。

### 3.2 UNIQUE 约束

```sql
CONSTRAINT uq_genealogy_user_user_genealogy
    UNIQUE (user_id, genealogy_id)
```

保证同一用户在同一族谱中只能有一个角色。`update_or_create` 操作依赖此约束实现幂等：

```python
GenealogyUser.objects.update_or_create(
    user=target_user,
    genealogy_id=genealogy_id,
    defaults={"role": role},
)
```

### 3.3 外键约束与级联策略

所有外键均使用 `ON DELETE CASCADE`：

```
user ←── genealogy.created_by
genealogy ←── member.genealogy
member ←── parent_child.parent
member ←── parent_child.child
member ←── marriage.spouse1
member ←── marriage.spouse2
member ←── member_generation_cache.member
genealogy ←── member_generation_cache.genealogy
```

级联删除链：
- 删除 user → 删除其创建的 genealogy → 删除所有 member → 删除所有 parent_child、marriage、cache
- 删除 member → 删除涉及该 member 的所有 parent_child、marriage、cache

这保证了数据的一致性——不会出现"孤儿记录"（引用了不存在的成员的父子关系或婚姻关系）。

## 四、代际缓存机制（物理优化核心）

### 4.1 问题背景

Q3（最长寿代际）和 Q5（早生成员）查询需要知道每个成员属于第几代。初版使用递归 CTE 实时计算：

```sql
WITH RECURSIVE generation_tree AS (
    -- 找根节点（没有父母的成员）
    SELECT m.member_id, 1 AS generation
    FROM member m LEFT JOIN parent_child pc ON pc.child_id = m.member_id
    WHERE m.genealogy_id = :gid AND pc.child_id IS NULL
    UNION ALL
    -- 向下递归
    SELECT pc.child_id, gt.generation + 1
    FROM generation_tree gt JOIN parent_child pc ON pc.parent_id = gt.member_id
)
SELECT member_id, MIN(generation) AS generation
FROM generation_tree GROUP BY member_id;
```

**性能问题**：
- 对于 5 万成员的大型族谱，递归 CTE 需要遍历整棵树
- 每次 Q3/Q5 查询都重复执行，耗时 ~14.8s
- 代际编号在成员关系不变的情况下是固定的，重复计算是浪费

### 4.2 缓存表设计

新增 `member_generation_cache` 表（迁移 0002），预存储每个成员的代际编号：

```sql
CREATE TABLE member_generation_cache (
    member_id BIGINT PRIMARY KEY,        -- 与 member 一对一
    genealogy_id BIGINT NOT NULL,        -- 所属族谱
    generation INT UNSIGNED NOT NULL,    -- 代际编号（始祖=1）
    computed_at DATETIME DEFAULT NOW(),  -- 缓存计算时间
    INDEX idx_mgc_genealogy_generation (genealogy_id, generation)
);
```

### 4.3 缓存构建算法

通过 BFS（广度优先搜索）在 Python 应用层构建代际映射：

```python
def _build_generation_map(genealogy_id):
    # 1. 加载所有成员和边
    member_ids = Member.objects.filter(genealogy_id=genealogy_id).values_list(...)
    edge_rows = ParentChild.objects.filter(...).values_list("parent_id", "child_id")

    # 2. 计算入度，找根节点（入度=0 的成员）
    indegree = defaultdict(int)
    for parent_id, child_id in edge_rows:
        children_map[parent_id].append(child_id)
        indegree[child_id] += 1
    roots = [mid for mid in member_ids if indegree.get(mid, 0) == 0]

    # 3. BFS：根节点 generation=1，子节点 = 父节点 + 1
    queue = deque(sorted(roots))
    for root_id in roots:
        gen_map[root_id] = 1
    while queue:
        current = queue.popleft()
        for child_id in children_map.get(current, []):
            next_gen = gen_map[current] + 1
            # 如果子节点已有更小的代际编号，不更新（取最小值）
            if gen_map.get(child_id) is None or next_gen < gen_map[child_id]:
                gen_map[child_id] = next_gen
                queue.append(child_id)

    # 4. 无法到达的节点归入 fallback 代际
    fallback = max(gen_map.values()) + 1
    for mid in member_ids:
        if gen_map[mid] is None:
            gen_map[mid] = fallback

    return gen_map
```

### 4.4 惰性重建策略

缓存不需要实时更新——当成员关系发生变化时，缓存可能过期。采用**惰性重建**策略：在查询时检查缓存是否需要重建。

```python
def _ensure_generation_cache(genealogy_id):
    member_count = Member.objects.filter(genealogy_id=genealogy_id).count()
    cache_count = MemberGenerationCache.objects.filter(genealogy_id=genealogy_id).count()
    if member_count != cache_count:
        _refresh_generation_cache(genealogy_id)
```

判断逻辑：如果 `member` 表的记录数与 `member_generation_cache` 表的记录数不一致，说明缓存过期，触发重建。

重建过程（`_refresh_generation_cache`）在事务中执行：
1. 删除该族谱的所有旧缓存记录
2. 使用 `bulk_create` 批量插入新缓存（batch_size=5000）

**为什么用成员数量变化作为失效条件？**
- 代际编号只在父子关系变化时改变
- 父子关系变化必然伴随成员数量变化（新增/删除成员）
- 用成员数量做判断是最轻量的检查（一次 COUNT 查询），无需额外的版本号或时间戳字段

### 4.5 优化效果

| 查询 | 优化前 | 优化后 | 原因 |
|------|--------|--------|------|
| Q3 最长寿代际 | ~14.8s | 首次~2.5s（建缓存），后续~0.16s | 避免重复递归 CTE |
| Q5 早生成员 | ~14.7s | ~0.50s | 同上 |

首次查询的 ~2.5s 是构建缓存的开销（BFS + bulk_create），后续查询直接从缓存表读取，只需一次简单的 GROUP BY + AVG 聚合。

## 五、SQL 查询优化

### 5.1 OR 条件 JOIN 的问题

初版的 Q1（配偶查询）和 Q4（未婚男性统计）使用 `OR` 条件连接：

```sql
-- Q1 初版：OR 条件
SELECT * FROM marriage ma
JOIN member m ON (ma.spouse1_id = :id AND m.member_id = ma.spouse2_id)
             OR (ma.spouse2_id = :id AND m.member_id = ma.spouse1_id);

-- Q4 初版：OR 条件 LEFT JOIN
SELECT * FROM member m
LEFT JOIN marriage ma ON m.member_id = ma.spouse1_id OR m.member_id = ma.spouse2_id
WHERE ... AND ma.marriage_id IS NULL;
```

**性能问题**：
- MySQL 对 `OR` 条件的 JOIN 无法高效使用索引
- 优化器可能选择全表扫描（`type: ALL`）而非索引查找（`type: ref`）
- Q4 在 5 万成员数据下耗时 ~121.8s

### 5.2 改写方案

**Q1 改写：UNION ALL 两段等值连接**

```sql
-- 配偶方向 1：spouse1_id = :id
SELECT 'spouse', m.* FROM marriage ma
JOIN member m ON m.member_id = ma.spouse2_id
WHERE ma.spouse1_id = %s

UNION ALL

-- 配偶方向 2：spouse2_id = :id
SELECT 'spouse', m.* FROM marriage ma
JOIN member m ON m.member_id = ma.spouse1_id
WHERE ma.spouse2_id = %s

UNION ALL

-- 子女
SELECT 'child', c.* FROM parent_child pc
JOIN member c ON c.member_id = pc.child_id
WHERE pc.parent_id = %s;
```

每段都是等值连接（`=`），MySQL 能独立为每段选择最优索引执行。

**Q4 改写：CTE + anti-join**

```sql
WITH married AS (
    SELECT spouse1_id AS member_id FROM marriage
    UNION                          -- UNION 去重，减少后续 JOIN 的数据量
    SELECT spouse2_id AS member_id FROM marriage
)
SELECT m.*
FROM member m
LEFT JOIN married mr ON mr.member_id = m.member_id
WHERE m.genealogy_id = %s
  AND m.gender = 'M'
  AND (YEAR(CURDATE()) - m.birth_year) > 50
  AND mr.member_id IS NULL;        -- anti-join：排除已婚
```

- `UNION` 汇总所有已婚 member_id（走 `idx_parent` 索引）
- `LEFT JOIN ... IS NULL` 做 anti-join（走 member 主键索引）
- 避免了 `OR` 条件导致的全表扫描

### 5.3 优化效果

| 查询 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| Q1 配偶查询 | ~2.3s | ~0.003s | 767x |
| Q4 未婚男性>50 | ~121.8s | ~0.26s | 468x |

### 5.4 页面级优化

`/analysis-page` 页面初版一次性加载所有族谱的全部成员到前端下拉框（~5 万条，~18MB），导致页面加载 ~3.4s。

优化方案：
1. 按族谱筛选：只加载当前选中族谱的成员
2. 数量截断：下拉列表限制前 500 条
3. 手动输入：提供 member_id 输入框作为备选

```python
# 优化后的 analysis_page_view
member_qs = Member.objects.filter(genealogy_id=selected_genealogy_id).order_by("member_id")
members = list(member_qs[:500])  # 限制 500 条
members_truncated = member_qs.count() > 500  # 标记是否截断
```

效果：~3390ms / 17.98MB → ~55ms / 176KB（61 倍提升）。

## 六、外键策略与数据完整性

### 6.1 CASCADE 删除链

```
user (删除)
  └── genealogy (CASCADE 删除)
        ├── genealogy_user (CASCADE 删除)
        ├── member (CASCADE 删除)
        │     ├── parent_child (CASCADE 删除，parent_id 或 child_id 匹配)
        │     ├── marriage (CASCADE 删除，spouse1_id 或 spouse2_id 匹配)
        │     └── member_generation_cache (CASCADE 删除)
        └── member_generation_cache (CASCADE 删除，genealogy_id 匹配)
```

### 6.2 为什么选择 CASCADE 而非 RESTRICT

| 策略 | 行为 | 优点 | 缺点 |
|------|------|------|------|
| CASCADE | 删除父记录时自动删除子记录 | 不会产生孤儿记录，应用层代码简单 | 误删可能导致大量数据丢失 |
| RESTRICT | 如果存在子记录则拒绝删除 | 数据安全 | 应用层需要手动处理删除顺序 |
| SET NULL | 外键设为 NULL | 保留子记录 | 本系统中外键不允许 NULL |

本系统选择 CASCADE 的理由：
- 族谱系统的业务语义天然支持级联（删除族谱 = 删除所有成员和关系）
- 避免应用层手动维护删除顺序的复杂性
- 配合 Django 的事务机制，删除操作是原子的

### 6.3 临时禁用外键检查

在批量导入数据时，临时禁用外键检查以避免导入顺序问题：

```sql
SET FOREIGN_KEY_CHECKS = 0;
-- 批量导入 parent_child、marriage 等表
LOAD DATA LOCAL INFILE ...;
SET FOREIGN_KEY_CHECKS = 1;
```

这是因为 `LOAD DATA` 按文件顺序逐行导入，如果子记录先于父记录导入，外键检查会失败。禁用外键检查后，导入完成后数据自然满足引用完整性。

## 七、设计决策总结

| 决策 | 选择 | 理由 |
|------|------|------|
| 存储引擎 | InnoDB | 事务、外键、行级锁、聚簇索引 |
| 字符集 | utf8mb4 | 完整 Unicode 支持（中文 + emoji） |
| parent_child 主键 | 复合主键 (parent_id, child_id) | 天然唯一性，聚簇索引无额外开销 |
| parent_child 索引 | 双向单列 + 组合索引 | 覆盖递归 CTE 的两个方向 + 覆盖索引 |
| member.name 索引 | B-tree + 前缀索引 | 完整索引用于排序，前缀索引用于搜索 |
| 代际查询 | 缓存表 + 惰性重建 | 避免重复递归 CTE，首次~2.5s，后续~0.16s |
| OR 条件 JOIN | 改写为 UNION ALL | 使 MySQL 能使用索引，Q4 从 121.8s 降至 0.26s |
